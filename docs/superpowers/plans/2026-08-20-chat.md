# Implementation Plan — Chat (Global + Direct Messages)

Source spec: `docs/superpowers/specs/2026-08-20-chat-design.md`

This plan is executed by a background agent working in its own git worktree
(`.worktrees/chat`, branch `feat/chat`), in parallel with another background
agent implementing `feat/world-activity-feed` in a separate worktree. **Both
agents branched from the same `main` commit and do not see each other's
files.** To avoid migration-number collisions at merge time:

- Do NOT reuse migration numbers 0034-0039 — those are reserved for the
  world-activity-feed feature (in flight in a sibling worktree).
- Start this feature's migrations at **0040**. Before applying anything live,
  re-check `git log --all --oneline -- supabase/migrations` and
  `ls supabase/migrations` on `main` (fetch latest) to confirm 0040+ is still
  free; if `main` has moved and 0040 is taken, pick the next free number
  instead — do not guess, verify.
- Migration numbers are just filenames; if a collision is discovered at
  merge-review time later, the orchestrating session will renumber — not
  your concern once you've verified against `main` at the time you apply.

Follow TDD throughout. Commit after each chunk. Run `jest`, `tsc` after each
chunk touching code. Do not push. Do not modify anything outside this
feature's files (do not touch world-activity-feed files even if you notice
something related). Update `docs/superpowers/PROGRESS.md` with a dated entry
when done. Clean up any scratch scripts before finishing.

## Chunk 1 — Schema + RLS migration

File: `supabase/migrations/00NN_chat.sql` (NN = verified free number, see
above), plus a companion `.verification.sql` following the project's existing
convention (see `0029_card_limit_deposit.verification.sql` for the pattern:
apply in a transaction, assert expected behavior, roll back).

Create:
- `chat_messages` table exactly as specified (id, sender_id, channel_type,
  conversation_id, recipient_id, body, created_at, deleted_at, deleted_by)
  with the check constraint tying channel_type to the nullability of
  conversation_id/recipient_id.
- `chat_blocks` table (blocker_id, blocked_id, created_at), PK on both cols.
- `chat_read_state` table (player_id, conversation_id, last_read_at), PK on
  both cols.
- Indexes: `(channel_type, created_at desc)`, `(conversation_id, created_at desc)`,
  `(sender_id, created_at desc)`.
- Enable RLS on all three tables. Policies exactly as described in the spec's
  RLS section (global visible to all authenticated; DM visible only to
  sender/recipient and not soft-deleted, except the sender can still see
  their own soft-deleted message).
- `revoke all on chat_messages, chat_blocks, chat_read_state from public, anon;`

Verification script: insert sample rows as two different impersonated
players (via `set local request.jwt.claim.sub`), confirm player A cannot
select player B's DM conversation with player C, confirm global rows are
visible to a third player, confirm the check constraint rejects a global row
with a non-null recipient_id. Roll back at the end.

## Chunk 2 — Core RPCs migration

File: `supabase/migrations/00NN_chat_rpcs.sql` (next number after chunk 1).

Implement, all `security definer`, `revoke ... from public, anon`,
`grant execute to authenticated`:

- `chat_send_message(p_channel_type text, p_recipient_id uuid, p_body text)
  returns chat_messages`
- `chat_list_global_messages(p_before_id bigint default null, p_limit int
  default 30)`
- `chat_list_conversations()`
- `chat_list_dm_messages(p_conversation_id uuid, p_before_id bigint default
  null, p_limit int default 30)`
- `chat_mark_read(p_conversation_id uuid)`
- `chat_block_player(p_target_id uuid)`, `chat_unblock_player(p_target_id uuid)`

Exact behavior per the spec (rate limit 2s, 500-char validation, blocked-sender
rejection in both directions, deterministic conversation_id via
`md5(least||greatest)::uuid`, clamp `p_limit` to max 100 server-side
regardless of client input, keyset pagination via `id < p_before_id`).

Verification script covering: rate-limit rejection on rapid resend, blocked
player cannot send in either direction, conversation_id is identical
regardless of who initiates, pagination returns correct page boundaries,
`chat_list_dm_messages` rejects a non-participant.

## Chunk 3 — Admin RPCs migration

File: `supabase/migrations/00NN_chat_admin.sql`.

- `admin_list_chat_messages(p_channel_type text default null, p_limit int
  default 50, p_before_id bigint default null)` — reuse
  `admin_require_admin()` guard (see `0012_admin_dashboard.sql` for the
  pattern), returns messages including soft-deleted ones with a `deleted_at`
  column so the admin UI can distinguish.
- `admin_delete_chat_message(p_message_id bigint)` — soft delete only
  (`deleted_at = now(), deleted_by = auth.uid()`), guarded by
  `admin_require_admin()`.

No admin UI page is required in this iteration — just the RPCs, wired later
if/when an admin chat-moderation UI is requested. Verification script:
non-admin caller rejected, admin caller succeeds, soft-deleted row excluded
from `chat_list_global_messages`/`chat_list_dm_messages` but present in
`admin_list_chat_messages`.

## Chunk 4 — Client API wrappers

File: `lib/chat/api.ts` (+ `lib/chat/api.test.ts`, mocking the Supabase
client per existing project conventions — check `lib/players/api.ts` or
similar for the mocking pattern used elsewhere).

Thin wrapper functions matching each RPC 1:1 (e.g. `sendMessage`,
`listGlobalMessages`, `listConversations`, `listDmMessages`, `markRead`,
`blockPlayer`, `unblockPlayer`), typed request/response shapes in
`lib/chat/types.ts`. No business logic beyond the RPC call itself — validation
lives server-side, but mirror the 500-char client-side check as a
`isValidMessageBody(body: string)` pure helper (unit tested) for immediate UI
feedback before the round-trip.

## Chunk 5 — Presentational components

Files under `components/chat/` (follow existing project component
conventions — check `components/world/` from the world-activity-feed
feature, or `components/map/` for structure/naming/test patterns):

- `MessageList` — renders messages oldest-to-newest, sender name links to
  profile, shows "message removed" placeholder for soft-deleted-but-visible
  own messages.
- `MessageInput` — textarea/input + send button, char counter (500 max),
  disables + shows cooldown countdown when rate-limited (based on last send
  timestamp passed as a prop, computed via `setInterval`/`Date.now()` diff,
  not a new server call).
  ("cooldown" duration must match the server's rate-limit window, 2s.)
- `ConversationList` — list of DM conversations with other participant name,
  last message preview, unread badge, click opens the conversation.
- `GlobalChatPanel` / `DmChatPanel` — compose `MessageList` + `MessageInput`
  + polling (4s interval via existing project polling hook/pattern if one
  exists, e.g. check how the map or world feed polls — reuse that hook
  rather than inventing a new one). Poll only while
  `document.visibilityState === 'visible'`.

Each component gets a co-located `.test.tsx` per project convention,
including at least one test at a narrow/mobile-portrait viewport (check how
existing responsive components are tested in this repo, e.g. search for
`matchMedia` mocks or viewport-resize test utilities already in use).

- Add "Chat" (or similar label, follow existing nav i18n/labeling
  conventions) to the main nav, alongside the "Dění ve světě" entry added by

  to copy (if it's already merged to main by the time you do this chunk; if
  not yet merged, just follow the pre-existing nav structure and add your
  entry independently — do not depend on the sibling feature's branch).
- Floating widget component (e.g. `components/chat/ChatWidget.tsx`), mounted
  once in the root layout, visible on all pages: bottom-right bubble with
  unread badge (desktop), fullscreen overlay on mobile portrait (top-left
  close button, bottom tab bar, input pinned above keyboard using
  `env(safe-area-inset-bottom)`/sticky positioning — check existing mobile-safe-area
  handling elsewhere in the app if any exists, otherwise use standard
  `position: sticky; bottom: 0`).
- Unread badge count: poll `chat_list_conversations()` periodically (can
  reuse the same 4s polling as the open chat, or a lighter/slower poll, e.g.
  15s, when the widget is collapsed — your call, document the choice in the
  PROGRESS.md entry).
